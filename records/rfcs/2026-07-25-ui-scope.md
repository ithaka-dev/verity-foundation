# RFC: UI scope

**Status:** draft
**Date:** 2026-07-25
**Author:** Claude (agent), for review by Peter
**Relates to:** spec §1, §2.3, §2.6, §2.7, §4.6, §8; invariants I1, I2, I6; CLAUDE.md C1, C4

## Problem

`verity-ui` has a reserved name and no scope. Meanwhile the spec incurs two human surfaces
without scoping either of them, and both are load-bearing:

- **Spend envelope** (§2.7) — "humans set boundaries once; agents transact autonomously within
  them." That sentence describes a UI. It is the only human-in-the-loop moment in the entire
  system and the last control between a prompt-injected agent and irreversible spend (§8).
- **Upgrade opt-in** (§2.3) — the MVP mitigation for a hostile "minor" release is *manual holder
  opt-in*. Manual implies a person, and a person implies a surface.

Neither appears in §5's MVP scope. So the question is not whether to build UI — the spec already
committed to some — but how much, and under what discipline.

The discipline matters because Verity's premise (§1) is "no app-store gatekeeper anywhere in the
path," and §4.6 deliberately has no catalog and no search. A careless reading concludes that UI is
in tension with the thesis. It isn't, but the reason why needs stating precisely, because the
failure mode is subtle and arrives late.

## Proposal

**Build many surfaces and make them good.** Onboarding quality is a legitimate product goal and
under-serving it does not make the system more decentralized — it makes it unused, which is a
worse outcome than a well-designed optional tool. Direction taken: onboarding-forward.

The discipline that keeps that safe is one test, applied to every surface:

> **If `verity-ui` disappeared tomorrow, would anything a developer or holder created stop
> working?**

If yes, it is a gatekeeper. If no, it is a tool. Everything below is designed to answer *no*.

### The risk is convenience, not count

The instinct is that more UIs mean more centralization. That is the wrong axis. Ten surfaces that
each wrap a public contract call centralize nothing. **One surface that is dramatically easier
than the alternative becomes the path in practice, however optional it is on paper.** De-facto
centralization arrives through convenience, not through permission.

This is not an argument for worse UI. It is an argument for making the alternative *visible and
real* rather than theoretical. Hence a standing requirement on every surface:

- **Show the underlying operation.** Every action displays the contract call, CLI equivalent, or
  IPFS manifest it produces. A user who wants to leave should be able to see exactly what to do
  instead — before they need to.
- **Export everything.** No state exists only inside the UI's backend.
- **Self-hostable, ideally static.** If it can be a static bundle pinned to IPFS, the "shut it
  down" story becomes uninteresting.
- **Never authoritative.** The chain is the source of truth. The UI reads and composes; it never
  grants, approves, or gates.

### Vocabulary: two words to avoid

**"Registration" → publishing tool.** A registration form implies someone can decline your
registration; that is an app store. What is actually wanted is a tool that deploys an
`AppManifest`, appends version→digest, sets upgrade pricing, and pins an `llms.txt`. Nothing is
granted — the output exists independently of whoever hosted the form. The word matters because
"registration" quietly invites a table of approved developers, and that table is the asset that
eventually gets subpoenaed, sold, or leaned on.

**"Catalog" → index.** A registry grants existence: you must be in it to be found. An index
observes what is already on-chain, anyone can run their own, and §4.6 discovery keeps working
without it. §4.6 forbids a *required* catalog, not an optional index. Build indexes freely; never
let one become the path.

### Surfaces

Priority order. 1–2 are obligations the spec already incurred; 3 is a prerequisite for a second
developer existing; the rest are onboarding quality.

**1. Spend envelope** (§2.7) — set the five dimensions on an ERC-4337 session key; show
consumption against each, or humans cannot calibrate a ceiling they have no feedback on.

> **Deferred with AA by [ADR 0002](../../docs/decisions/0002-defer-account-abstraction.md).** With
> no envelope to configure, this surface has nothing to render; surfaces 2 and 3 lead in the
> interim. It returns as the top priority at the mainnet gate — and note it is a *gate*, so this
> UI is on the critical path to real value, not a follow-up to it.

> **Hard constraint: non-custodial.** §2.7's whole argument is that the boundary is only real at
> the layer the agent cannot edit. If this UI holds the owner key, the editable layer has moved
> from the agent to the operator and the argument collapses — quietly, while still looking
> correct. Signing is local, always. This is the one place where onboarding convenience must lose.

**2. Upgrade decision** (§2.3) — notify that a version exists, present its price, sign the move.
Now the leading human surface, since #1 is deferred.

> Reframed by [ADR 0003](../../docs/decisions/0003-holder-initiated-upgrades.md). This is **not** a
> security screen that must confess its limits — it is a purchase decision, and the holder is
> already protected by default: doing nothing keeps them on the exact digest they licensed,
> indefinitely. Sitting on an old version forever is a supported outcome, not a failure state, and
> the UI should present it as such rather than nagging.
>
> It remains true that **you cannot diff a digest**, and the UI should say so plainly rather than
> rendering a developer-supplied changelog as if it were verified. But that is caveat emptor on a
> new purchase, the same as the original one — not a mitigation failing to do its job.
>
> Hard requirement: **no auto-update affordance, no "keep my tools current" toggle.** Convenience
> features here would reintroduce auto-follow, which ADR 0003 refuses outright.
>
> For a stateful app this is a **guided three-step flow**, not a button: mint (transaction) →
> authorize migration (EIP-712 signature) → burn (transaction, after migration verifies). The
> consents are deliberately separate — minting says "I want this version," authorizing says "move
> this instance's data and retire the old one," and a holder may want the first without the second
> ([RFC app-lifecycle-contract](2026-07-25-app-lifecycle-contract.md)). Design the flow to carry
> someone through three signatures without losing them; do not design it to need fewer.

**3. Developer publishing tool** — deploy `AppManifest`, append version→digest, set upgrade
pricing, pin the `llms.txt` manifest. Must support hardware-wallet signing: the `AppManifest`
writer is Tier 0 in [the secrets RFC](2026-07-25-secrets-management.md), and rightly so.

**4. Holder view** — licenses held, instances running, state, transfer, kill/restart. This is
§2.6's "chest of tools" made visible, and transfer is where §2.6's ownership-continuity claim
becomes tangible rather than theoretical.

**5. Attestation evidence viewer** — `licensed_digest == attested_digest` rendered legible to a
human. Not load-bearing (agents verify programmatically per I1) but it is the thesis made visible,
and probably the most persuasive artifact the project can show. See the I1 caveat below.

**6. Discovery index** — last, optional by construction, and only once 1–5 exist. Building it
early risks it becoming load-bearing before anyone notices.

## Why now

The name is reserved and the two obligations already exist in the spec, so the scope question is
open whether or not it is written down.

More particularly: **the first UI defines what users believe the system is.** Onboarding decisions
calcify faster than architecture ones, because they propagate into documentation, screenshots,
tutorials, and every third-party integration built against them. A custody shortcut taken for
launch convenience is not a UI decision that can be revisited later — it becomes the thing
everyone built on.

## Impact on invariants

- **I1** (never trust an endpoint before verification) — the attestation viewer must not become a
  second, weaker trust path. A green check in a web page is *the UI's claim*, not an attestation.
  Verification is the agent-side verifier's job (§4.5) and must stay there. Recommendation: the
  viewer displays evidence and shows how to verify it independently; it must never be the thing a
  human relies on to decide the system is honest.
- **I2** (spend limits live in the session-key policy) — the UI *writes* policy and *displays*
  consumption. It never enforces. Any UI-side check is a convenience, never a control, and should
  be commented as such where implemented.
- **I6 / C4** ("trust-minimized", never "trustless") — onboarding copy is the single most likely
  place for "trustless" to appear, because it is shorter and sounds better. Explicit lint or
  review rule on user-facing strings.
- **C1** (`services/` are navigation aids, never on the product path) — `verity-ui` is product and
  lives in its own repo. None of these surfaces belong in this repo's `services/`.
- **§1** (no gatekeeper in the path) — preserved by the disappearance test and the replaceability
  requirements, not by restraint in how many surfaces we build.

## Alternatives

**No UI; agent-only and CLI-only.** Ideologically clean, and genuinely the most censorship-
resistant answer. Rejected: §2.7 and §2.3 require human acts, so "no UI" means those acts happen
through hand-rolled contract calls, which caps participation at people who can do that. That is
its own kind of gatekeeping — by expertise instead of by permission.

**Minimal UI: only the two spec obligations.** The conservative fallback. Rejected per the
onboarding-forward direction, but worth recording as the position to retreat to if the
replaceability requirements prove unenforceable in practice.

**Fold the UI into `verity` (the front door).** Rejected: the front door is static explanatory
content, while these are applications with wallet interaction and a different risk and deploy
profile. Keep the marketing surface and the signing surface apart — mixing them means a copy edit
ships alongside code that touches keys. The attestation viewer (#5) is the one plausible exception,
since it is largely demonstrative.

**Third-party UIs only — publish good APIs and let the ecosystem build.** This is arguably the
healthy end state, and it is what the replaceability requirements are building toward. Rejected
for now only because no ecosystem exists yet. It does argue for treating the public API and any
SDK as first-class from the start rather than as an afterthought extracted later.

## Open questions

1. ~~**Custody vs. onboarding.**~~ **Settled 2026-07-25: nothing custodial or semi-custodial.
   Account abstraction is the ceiling.** Embedded wallets, social recovery services, and
   semi-custodial accounts are all excluded. Onboarding quality must be achieved within that
   constraint — the practical route is passkey-owned ERC-4337 accounts, which give Face ID
   ergonomics with keys that never leave the device. The consequences for the payment path are
   substantial and are worked out in
   [RFC non-custodial-payments](2026-07-25-non-custodial-payments.md).
2. ~~**Does the holder view require an indexer?**~~ **Settled 2026-07-25: eventually yes, and it
   must be non-authoritative, replaceable, and optional.** ERC-1155 gives `balanceOf(holder, id)` but
   no enumeration, so "all licenses held" means indexing `TransferSingle`/`TransferBatch` events. On-chain
   enumeration is the alternative and it is expensive for no benefit.

   Three constraints, all following from the disappearance test:
   - **The UI must work without it, degraded.** Given a token id — from a purchase receipt, a URL, or
     manual entry — everything must function. The indexer answers *"what do I have?"*, never
     *"is this valid?"*.
   - **Anyone can run their own**, and the schema is documented. An indexer nobody else can stand up
     is a gatekeeper with extra steps.
   - **It is never on the verification path.** No attestation or license check may consult it.

   **MVP needs none** — one tool, one license, nothing to enumerate. Build it when a holder plausibly
   owns more than a handful, not before.
3. ~~**Where does the attestation viewer live?**~~ **Settled 2026-07-25: `verity`, the front door.**
   It is demonstrative rather than transactional — it displays evidence and signs nothing, so it
   does not carry the wallet-interaction risk that motivated keeping the marketing surface and the
   signing surfaces apart. And it is the artifact that makes the thesis legible, which is exactly
   what the front door is for.
4. ~~**Can the UI be a static bundle pinned to IPFS?**~~ **Settled 2026-07-25: yes, and this is a
   design constraint rather than an aspiration.** Every surface here reads chain state and signs
   locally; none needs a server. Custody is non-custodial by decision, so there are no secrets to
   hold, and verification consumes the published compose plus a quote, both fetchable client-side.

   **Any requirement for a backend is a deviation that must be justified in writing**, not a default
   that accumulates. The one legitimate candidate is the indexer (Q2) — which is why it is
   constrained to be optional and replaceable, so a static build degrades rather than breaks.

   This is what makes the disappearance test pass trivially instead of by argument: a bundle pinned
   to IPFS cannot be shut down, so "optional in principle" and "optional in practice" stop diverging.
5. ~~**Who is the actual first user?**~~ **Settled 2026-07-25: agents.** The human configures once
   and steps out; the spec's primary scenario (§1) is the design centre, not an advanced mode.

   **This does not reduce the UI work — it changes its character, and raises the bar.** A surface
   used once has no learning curve to amortise: there is no second session in which the user
   figures out what they got wrong the first time. Daily-use software can be mediocre on day one
   and taught over a month. A one-shot configuration tool has to be right immediately, for someone
   who will never build fluency with it.

   So "many UIs, good onboarding" and "agent-first" are compatible, and the reading that reconciles
   them is: **many entry points for a human to accomplish one setup task and leave**, not many
   places for a human to live. Depth of daily-use features is the wrong investment; clarity,
   defaults, and irreversibility warnings at the single moment of contact are the right one.

   Two carve-outs where a human returns repeatedly, and which therefore do behave like conventional
   applications:
   - **The developer publishing console** — used on every release, by someone building fluency.
     Also the surface used *first* chronologically, since nothing can be bought until something is
     published.
   - **The upgrade decision** (§2.3) — recurring, and per
     [RFC app-lifecycle-contract](2026-07-25-app-lifecycle-contract.md) a guided multi-step flow.
