# L-04 re-run: the verifier still refuses, on dstack 0.5.9

**Date:** 2026-08-08
**Platform:** Phala Cloud, workspace `verity`, node 26 (`prod5`), `--image dstack-0.5.9`, CLI v1.1.19
**Status:** passed, both directions
**Relates to:** [ADR 0009](../../docs/decisions/0009-verification-model.md), invariant I1;
[the 0.5.7 run](2026-07-31-l04-verifier-refuses-on-mismatch.md);
[L-02/L-03 on 0.5.9](2026-08-08-l02-l03-continuity-on-dstack-059.md)

## Why

L-04 was measured on dstack 0.5.7, which Phala no longer offers. The attestation *structure* —
`MR-CONFIG-ID` V1, the RA-TLS carrier, the quote layout — rested entirely on a version nobody can
deploy. L-02 and L-03 re-verified state continuity on 0.5.9 earlier the same day and explicitly did
not cover this.

## Result

```

      compose_hash           passed
      images_pinned          passed
      licensed_image_present passed
      quote_signature        passed
      tcb_status             passed
      mr_config_id           passed
      boot_measurements      skipped (no OS image reference supplied)

[4] the same compose with ONE byte appended               REFUSED
      mr_config_id           FAILED
        expected 01bf666e5da961fc3333f463052ece1bddf8a58c0248a4213196b1be8c97aeb763000…
        measured 0161865f96ac0949778cfb515224b40abcfaf911c1b8558c4ddc7b0d3001360580000…
```

Quote 5010 bytes; compose 16398 bytes, 16399 after the added byte.

**`MR-CONFIG-ID` is still V1 on 0.5.9** — both values begin `01`, and the expected value is
`0x01 ‖ sha256(app-compose.json) ‖ 0x00×15` exactly as ADR 0009 describes. `tcb_status` passed, so
the platform's TCB was acceptable to the default policy without any widening.

The refusal is the property. An accept-only run cannot distinguish "the check passed" from "the
check did not run", which is the self-degradation ADR 0009 rule 3 is written against.

## What this run does **not** cover

**`boot_measurements` has still never executed against real hardware — on any version.** It reported
`skipped` here, and it would have on 0.5.7 too, because `examples/verify-attestation.rs` has no flag
for supplying an OS image reference. It accepts `--attestation`, `--compose` and `--image-digest`
and nothing else.

That is worth stating plainly: the verifier **bundles** reference data for `dstack-0.5.6` through
`0.5.10`, and check 7 of 7 has never been run against a live deployment. So the bundled
measurements for 0.5.9 are unverified against a real 0.5.9 CVM. If they are wrong, nothing in this
project would currently notice — ADR 0014 point 4 ships that data precisely so verification works
offline, which makes its correctness load-bearing and, at present, assumed.

Closing it needs a runner flag, not a protocol change.

## Fixes made to the harness before running

- **The OS image is pinned** (`--image ${DSTACK_IMAGE:-dstack-0.5.9}`). It was previously
  auto-selected, which is how a measurement comes to describe whatever was newest that day — the
  situation that made this re-run necessary.
- **The attestation wait is bounded.** `until … do sleep 15; done` had no deadline and would hang
  forever if `is_online` were renamed. Not hypothetical: `phala logs` moved its CVM argument to a
  flag and broke L-02/L-03 in exactly that way.
- **`os_image_hash` does not exist in the attestation.** A probe added for this run printed
  `unknown` because it looked for a field that is not there; `tcb_info` carries
  `mrtd / rootfs_hash / rtmr0-3 / event_log / app_compose`, and MRTD *is* the OS image measurement.
  Now records `mrtd`, so a run's platform is identifiable from the evidence rather than from what
  the operator believes they pinned.

Unlike L-02 and L-03, the rest of this script was correct: its `phala deploy`, `cvms attestation`
and `cvms delete` calls all still match the CLI, and it already tore down on any exit via a trap.
